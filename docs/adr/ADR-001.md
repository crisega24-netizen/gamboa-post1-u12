# ADR-001: Capas simples para la persistencia; el seam de notificación ya cubre el próximo cambio conocido

- **Estado:** Aceptado
- **Fecha:** 2026-10-31
- **Autor:** Juan Sebastián Gamboa Cristancho
- **Alcance:** Sistema de Solicitudes de Reembolso de Gastos Corporativos (`reembolsos-integrado`)

## Contexto

Tras integrar Chain of Responsibility (RF1), Strategy (RF2) y Observer (RF3), corresponde decidir si el sistema debe migrar a arquitectura **Hexagonal** completa, con puertos e interfaces intermedias para todas sus dependencias externas, o mantenerse en **capas simples**.

El criterio de la Guía (sección 6.2) es que Hexagonal vale la pena «en sistemas que sobrevivirán 3 años o más **con cambios de infraestructura**». No basta con que el sistema dure; tiene que haber cambios de infraestructura previstos. El sistema tiene dos dependencias externas, y el criterio se evalúa por separado para cada una, con datos del propio proyecto:

| Dependencia externa | Cambio de infraestructura previsto | Superficie de contacto hoy |
|---------------------|------------------------------------|----------------------------|
| **Persistencia** (Spring Data JPA + H2) | **Ninguno.** No existe plan de cambiar el motor de base de datos. | Una sola clase la usa: `SolicitudReembolsoService`, con 3 métodos (`findByEmpleadoIdAndEstado`, `findById`, `save`). |
| **Notificación a Contabilidad** | **Sí, con fecha:** integración por API externa el próximo trimestre para el pago de las solicitudes aprobadas. | El servicio ya no conoce a los notificadores. Depende solo de `List<ObservadorCambioEstado>`. |

Además, el dominio ya es independiente de JPA. `SolicitudReembolso` es un objeto Java plano, y su mapeo está en `META-INF/orm.xml`. El costo típico de Hexagonal (una entidad JPA separada del modelo de dominio, más los mappers entre ambas) aquí no aportaría nada.

## Alternativas consideradas

1. **Hexagonal completa:** un puerto `RepositorioSolicitudes` con su adaptador JPA, y un puerto de salida para notificaciones con sus adaptadores.
2. **Hexagonal solo para la persistencia:** el puerto de persistencia, dejando la notificación como está.
3. **Capas simples (elegida):** el servicio depende directamente de `RepositorioSolicitudesJpa`, y la notificación se mantiene sobre `ObservadorCambioEstado`.

Las alternativas 1 y 2 introducen un puerto de persistencia **sin ningún caso de uso que lo requiera**. La alternativa 1, además, duplicaría en la notificación la abstracción que `ObservadorCambioEstado` ya ofrece.

## Decisión

**Persistencia — capas simples.** `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, sin un puerto intermedio. Para la persistencia no se cumple el criterio de la Guía, porque no hay un cambio de infraestructura previsto. Un puerto hoy sería una abstracción especulativa (YAGNI) con una única implementación posible. Tampoco pasa el test de explicabilidad: la única oración que lo justificaría sería «por si algún día cambia la base de datos».

**Notificación — ningún cambio estructural.** `ObservadorCambioEstado` ya es el seam necesario para el único cambio de infraestructura con fecha conocida. Cuando llegue la integración de Contabilidad, la llamada a la API externa se implementará como un nuevo `ObservadorCambioEstado` ubicado en `infraestructura`, por ejemplo `infraestructura.contabilidad.NotificadorContabilidadApi`, que reemplazará a `NotificadorContabilidad`. Esa clase de infraestructura implementa una interfaz de `procesamiento`, y esa dirección de dependencia está permitida. La Regla 1 de ArchUnit prohíbe la dirección contraria, que `procesamiento` dependa de `infraestructura`. Ni `SolicitudReembolsoService` ni los otros dos observadores cambian.

## Consecuencias

**Positivas**

- No se agregan interfaces ni adaptadores de persistencia sin un caso de uso real que los justifique, y el código sigue siendo directo de leer.
- El único cambio de infraestructura con fecha (la API de Contabilidad) ya tiene su punto de extensión listo, sin tocar el servicio de aplicación.
- La deuda aceptada es pequeña y está acotada. Si algún día se necesita el puerto de persistencia, basta con una interfaz `RepositorioSolicitudes` de 3 métodos en `aplicacion`, que `RepositorioSolicitudesJpa` puede extender para que Spring Data la implemente, y cambiar el tipo en un solo constructor. Gracias a `orm.xml` no se necesitan mappers, y la Regla 1 de ArchUnit garantiza que ninguna otra clase de `procesamiento` dependa de JPA mientras tanto.

**Negativas**

- Si en el futuro se cambia de motor de base de datos, el puerto deberá introducirse retroactivamente. Se acepta esa deuda técnica de forma consciente.
- El servicio sigue acoplado a Spring Data. Sus pruebas unitarias aisladas necesitarían un *mock* de `JpaRepository`, por eso hoy se cubre con la prueba de integración `@SpringBootTest`.
- La asimetría (un seam para la notificación y ninguno para la persistencia) puede parecer una inconsistencia a un revisor que espere puertos en todas las dependencias externas, si no lee este ADR.
- **Riesgo conocido para la integración con Contabilidad.** Hoy los observadores se ejecutan en secuencia, en el mismo hilo. Si la API externa falla y lanza una excepción, los observadores siguientes no se ejecutarían. Al implementar `NotificadorContabilidadApi` habrá que aislar ese fallo (capturar y registrar el error, o reintentar) dentro del propio observador. No se resuelve hoy porque los tres notificadores actuales no pueden fallar.

## Señales que harían revisar esta decisión

- Un plan concreto para cambiar de motor de base de datos, o para leer o escribir las solicitudes en un segundo almacenamiento, como un *data warehouse*. → Introducir el puerto de persistencia.
- Una segunda aplicación que necesite reutilizar `SolicitudReembolsoService` sin JPA, por ejemplo un proceso por lotes con otro origen de datos.
- Que la integración de Contabilidad requiera más que un observador nuevo, por ejemplo una respuesta síncrona que modifique el estado de la solicitud. → Reevaluar si la notificación necesita un puerto propio en vez de un observador.
